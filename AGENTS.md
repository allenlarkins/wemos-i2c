# Agent Rules — Esp Rotary Controller

You are working in a PlatformIO firmware project for a physical device: a Wemos
D1 Mini (ESP8266) driving a 1.3" SH1106 OLED (I2C, address `0x3C`) and an EC11
rotary encoder with push button. Changes here are eventually compiled and
flashed to real hardware.

## CRITICAL: User Consent and Scope Rules

You MUST follow these rules strictly:

1. **Never exceed the user's request** - Do exactly what the user asks, nothing
   more. Do not "improve" or "enhance" beyond the stated scope.

2. **Never make changes without explicit approval** - Before modifying ANY file:
   - Show the user exactly what you plan to change
   - Wait for their explicit confirmation ("yes", "go ahead", "do it", etc.)
   - If they haven't approved, DO NOT proceed

3. **Ask, don't assume** - If the user's request is ambiguous:
   - Ask clarifying questions first
   - Present options and let them choose
   - Never guess at their intent

4. **Read-only by default** - When investigating or troubleshooting:
   - Only read files and gather information
   - Present findings and recommendations
   - Wait for user instruction before making any changes

5. **One change at a time** - When making approved changes:
   - Make the minimum change needed
   - Show what was changed
   - Let the user verify (and, where possible, rebuild) before proceeding

6. **No unsolicited modifications** - Never:
   - "Clean up" code the user didn't ask about
   - Add features they didn't request
   - Refactor working logic (e.g. `Menu`, encoder handling) without being asked
   - Fix issues they haven't mentioned

7. **Respect "no"** - If a user declines a suggestion, do not:
   - Repeat the suggestion
   - Make the change anyway
   - Try to convince them otherwise

## Environment Context

- Working directory is the PlatformIO project root (contains `platformio.ini`).
- Single build environment: `env:d1_mini` (`platform = espressif8266`,
  `board = d1_mini`, `framework = arduino`).
- Source lives entirely in `src/`: `main.cpp` (setup/loop, pin definitions,
  encoder/button handling), `Menu.h`/`Menu.cpp` (reusable, instantiable menu
  class with title, fixed-capacity item array, and parent pointer for
  navigation).
- Repo is standalone at `github.com/allenlarkins/wemos-i2c`, default branch
  `main`.

## Project Interaction Model

### 1. Source Files (Primary Interface)
`src/*.cpp`, `src/*.h`, and `platformio.ini` are the user-facing surface.
These are what you read, discuss, and edit — always with approval per the
rules above.

### 2. Build Verification (Safe, Read-Only w.r.t. Hardware)
`pio run` (or `& "$env:USERPROFILE\.platformio\penv\Scripts\platformio.exe" run`
if `pio` isn't on `PATH`) compiles the firmware without touching any physical
device. **Always build after a source change and before telling the user it
works** — this is the only automated verification available; there is no
hardware-in-the-loop testing.

### 3. Flashing (Hardware-Affecting — Requires Explicit Approval)
`pio run -t upload` writes to the physical board over serial. This is a
real-world action on real hardware and must never run without the user
explicitly asking for it in that moment.

### 4. Git Operations (Shared State — Requires Explicit Approval)
Commits, pushes, branch changes, and remote/repo creation are visible to
others and affect shared history. Confirm before each one; never force-push,
rewrite published history, or delete branches without being asked.

## File Structure Knowledge

### Editable (Primary Interface)
- `src/main.cpp`, `src/Menu.h`, `src/Menu.cpp` — application code
- `platformio.ini` — board/platform config and `lib_deps`
- `.gitignore`, `README.md` — project metadata

### Generated — Do Not Hand-Edit
- `.pio/` — build artifacts (gitignored); regenerated by `pio run`
- `.vscode/c_cpp_properties.json`, `.vscode/ipch` — IDE-generated
  (gitignored); regenerated by the PlatformIO IDE extension

### Sensitive (if/when added)
- Wi-Fi credentials, API tokens, or other secrets must never be hardcoded or
  committed. If networking is added later, use a gitignored header (e.g.
  `secrets.h`) or build-time defines, not literals in `main.cpp`.

## Best Practices

1. **Build before declaring done** - Run `pio run` after every source change.
2. **Minimal, incremental changes** - Match the specific ask; don't bundle
   unrelated edits into the same change.
3. **Preserve existing conventions** - Named `constexpr` layout/pin constants
   instead of magic numbers, fixed-capacity C arrays instead of
   heap/`std::vector`/`new` for menu or state data (deliberate embedded
   constraint — keep it that way unless asked to change it).
4. **Comment sparingly** - Only for non-obvious hardware/timing rationale
   (e.g. debounce intervals, pin-to-silkscreen mappings), never to restate
   what the code already says.
5. **Flag physical-wiring impact** - If a change alters a pin assignment,
   call out that the user may need to physically rewire the device.

## Safety Guidelines

- NEVER run `pio run -t upload` (or any flashing command) without explicit,
  in-the-moment user approval.
- NEVER commit or push without explicit approval.
- NEVER force-push, amend published commits, or delete branches.
- NEVER hardcode or commit secrets (Wi-Fi credentials, API keys) if
  networking/cloud features are added later.
- ALWAYS verify `pio run` succeeds before reporting a change as working.
- ALWAYS confirm with the user before writing, editing, or deleting any file.

## Common Tasks

### Adding a Menu / Submenu
1. Define a `MenuItem[]` array and a `Menu` instance for the new screen.
2. Wire its parent pointer for Back navigation, and add it as a `submenu` on
   the appropriate parent item.
3. Show the diff and wait for approval before applying.
4. `pio run` to confirm it compiles.

### Adding a Library Dependency
1. Add the library to `lib_deps` in `platformio.ini`.
2. `pio run` to confirm PlatformIO resolves and compiles it.
3. Report the resulting RAM/Flash usage delta from the build output.

### Changing Pin Assignments
1. Update the `constexpr` pin definitions and their wiring comments in
   `main.cpp`.
2. Explicitly tell the user which physical connections need to change.
3. `pio run` to confirm the change still compiles.

### Flashing / Testing on Hardware
1. Confirm the correct serial port is connected and ask the user before
   running `pio run -t upload`.
2. Never assume hardware is connected — ask first.
